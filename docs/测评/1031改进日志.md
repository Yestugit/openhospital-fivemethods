看过这四个参考仓库后，我的判断是：**我们应保留连续学习研究需要的能力，减少用户必须理解的对象、填写的策略和编写的调度代码。**参考仓库各有取舍，不能直接按接口数量判断好用程度。

**1. 参考仓库怎样组织测评**

| 仓库 | 测评实现方式 | 可以参考的地方 |
|---|---|---|
| [MemEngine](C:/Users/12084/Desktop/研究生/code/MemAtlas/reference-memory-frameworks/MemEngine/README.md) | 以 HotPotQA、对话等任务脚本组织 Agent、Memory 和评分；自动选择功能接收用户定义的评价函数 | 接入约定直接，容易理解；但用户需要修改较多任务脚本，通用实验调度较少 |
| [MemoryData](C:/Users/12084/Desktop/研究生/code/MemAtlas/reference-memory-frameworks/MemoryData/README_ZH.md:162) | 方法预设＋数据集预设，统一启动；内部处理历史写入、回答、评分、状态保存和失败重试 | **普通用户选预设即可运行**，无需自行拼装测评对象；其内部仍有较多方法和数据集专用分支 |
| [MemEvolve](C:/Users/12084/Desktop/研究生/code/MemAtlas/reference-memory-frameworks/MemEvolve/README.md) | 提供固定搜索 Agent 和数据集脚本，通过 Memory Provider 切换记忆；另有候选记忆系统生成、比较和选择流程 | **场景接入由仓库预先完成**，用户主要选择方法和实验规模；它的元演化流程与我们的连续学习曲线有不同目的 |
| [MemTools](C:/Users/12084/Desktop/研究生/code/MemAtlas/reference-memory-frameworks/MemTools-public/README.md:50) | 分开组织 Benchmark、评测协议和记忆流水线；协议负责训练、写入、检索与测试 | 数据与调度分离值得参考；但它公开了更多协议和组件组合，选择数量也较多 |

几个关键实现区别：

1. **MemEngine 把较多测评逻辑交给任务脚本。**我们的 Runner 承担通用执行、统计和恢复，可以减少用户重复写这些代码。
2. **MemoryData 把接入差异收进预设和适配器。**我们可以提供同样清楚的标准运行路径，同时保留方法的必要数据要求。
3. **MemTools 让用户组装记忆流水线和选择协议。**我们的目标是集成完整 Memory 方法，适合少暴露组件组合。
4. **MemTools 的部分协议会在测试前统一整合记忆。**我们应继续遵守各方法的原生更新规则，冻结测试与演化时机分别处理。

**2. 我们考虑了哪些额外内容**

我们除了历史问答和训练后测试，还覆盖了：

1. 多检查点连续学习、重复病例和跨科室任务流。
2. 即时、批次、延迟反馈及反馈后的学习。
3. 冻结保护、实际完成与学习进度、检查点恢复。
4. 实际使用的记忆来源，以及 Agent、Memory、评分等资源统计。

这些与 MemoryRSI 研究目标有关，值得保留。**当前较大的使用负担，是用户需要直接参与组织其中不少细节。**

**3. 我建议优先精简这些用户接口**

| 当前位置 | 精简建议 |
|---|---|
| **公开的实验对象较多** | 普通测评围绕 `ExperimentConfig`、`ExperimentRunner` 使用；`ExperimentSpec`、`MethodRun`、`MatrixRunner` 作为内部实现，减少普通用户接触 |
| **标准问答还需创建 `answerer`** | 内置 Benchmark 提供默认答题器和评分配置，用户填写模型即可；自定义回答逻辑时再提供回调 |
| **连续学习要求编写 `train_batch`、`test_batch`** | 内置场景提供现成批次处理；自定义场景优先要求一个单案例 Agent 接口，由框架组织训练和测试 |
| **配置和执行都能覆盖 Benchmark、协议等内容** | 主要选择集中在实验配置中，减少同一设置在多个位置填写或覆盖 |
| **通用策略选项较多** | 历史去重、案例隔离、快照频率等采用明确默认规则；即时／延迟反馈等研究变量只在相关实验中提供 |
| **普通与连续实验的结果表达不同** | 提供一致的报告字段和查看方式，用户直接看到分数、学习曲线、成本及失败情况 |

`runner.check(...)` 可以保留为可选检查；正常执行时自动完成必要校验。`ExperiencePlan` 暂时保留其连续学习计划职责，先解决重复配置和批次回调负担。

**4. 最值得先做的三项**

1. **内置 Benchmark 给出完整预设：数据、默认答题流程、原生评分和必要条件。**
2. **标准测评只需配置即可运行；自定义 Agent 只接入一个明确的案例执行接口。**
3. **连续学习的批次、冻结和检查点由框架组织，用户主要指定训练数据、测试数据和测试位置。**

训练／测试划分、真实反馈、案例隔离、冻结和方法更新时机，都影响实验含义，应继续明确保留。特殊场景按需适配，公共接口优先服务这些主要流程。
