# EMem 耗时排查与 Memora 快照修复

运行目录：`.mematlas/efficiency-formal-20261107-restart`。本次只读取计量、修复恢复保障，不改变记忆算法、病例、模型或检索预算。

## EMem 为何慢

以第 1 轮已完成 20 例的持久化计量为依据：

| 项目 | EMem | Memora |
|---|---:|---:|
| 完整流程秒 | 15920.1208945 | 8392.2309383 |
| 记忆方法墙钟秒 | 14471.7328199 | 6708.0904495 |
| 检索累计秒 | 13030.21 | 1005.44 |
| 检索次数 | 160 | 155 |
| 平均检索秒 | 81.44 | 6.49 |
| 写入累计秒 | 1441.38 | 5701.40 |
| 持久化秒 | 40.7128251 | 99.3424627 |
| 测量秒 | 177.9145491 | 178.2483265 |

来源为各方法 `activity/measurement-1.json` 与 `events-*.jsonl` 中配对的 start/end。分项可能嵌套，不能直接当作互斥分项相加。Memora 写入包含未提交失败尝试成本。

EMem 第一轮约 91% 的完整流程墙钟属于记忆侧，约 90% 的记忆侧时间用于检索。每例平均 8 次检索，串行等待每次约 81 秒。固定的官方 `retrieve_structuring_conversation_enhanced_v2` 会调用查询实体抽取与候选 EDU 的 LLM 筛选。无 PPR 配置仍保留这些步骤；当前医院逐决策使用已有记忆，因此会频繁调用。

排查时第二轮前 4 例共有 31 次已结束检索，平均 77.25 秒。当前不能据此认定记忆增长使检索迅速变慢。并行方法共享物理内存、磁盘、网络和 API 容量，资源竞争存在，尚无反事实对照可精确归因其耗时比例。没有为提速改为纯向量检索或降低预算。

## Memora 第 38 例暂停

原生 worker 首先在 `NativeMemora.export_state -> canonical(rows)` 完整向量 JSON 编码时发生 `MemoryError`。随后公共存储统计访问长于 Windows MAX_PATH 的 Chroma `index_metadata.pickle`，产生 `FileNotFoundError` 并覆盖了外层异常。文件通过扩展路径实际可见，不能解释为原生数据库丢失。

修复：

- 逐行流式输出与原来完全相同的 canonical JSON 数组，保留原生枚举顺序、全部向量、缓存、格式与校验值；不再同时构造整库 Python 向量副本、整段 JSON 字符串和编码字节。
- 公共存储枚举和 stat 使用 Windows 扩展路径；NativeMemora 显式保持扩展路径。
- 未改变公共 checkpoint schema，原快照可直接校验恢复。

验收：Memora 原生 10 项测试通过，包含实际 Chroma 1100 条记录跨越索引持久化阈值、超过 260 字符的路径、精确字节/向量对照、禁止模型调用的恢复、损坏检测和中断临时文件清理。公共执行/计量/看板/JSON/并行 58 项测试通过。

修复审计与原文件备份：`repairs/20261109-memora-checkpoint-path/repair-audit.json`。由并行父执行器接受带源码哈希的单方法重启请求，Memora attempt 3 从已提交 37 例恢复。第 38 例已有诊疗输出保留，补未提交阶段；原失败时间和请求成本保留。EMem 原进程持续运行。

## 并行影响与 EMem 输出格式排查

不能仅凭记忆操作耗时高就归因于算法本身。利用 Memora 暂停期间的自然窗口检查 EMem：

| UTC 窗口 | 条件 | 已结束检索数 | 平均秒 |
|---|---|---:|---:|
| 12:00–12:27 | 并行 | 14 | 74.88 |
| 12:30–12:53 | Memora 停止 | 12 | 78.70 |
| 13:00–13:29 | 恢复并行 | 15 | 80.51 |

这是不同病例/查询和不同记忆大小的自然窗口，不能视为严格因果对照。停止 Memora 后没有明显加速，与“主要由 API 并发限流拖慢”的解释不符；EMem 抽样账本中没有失败或重试。与此同时，机器内存占用约 90%、分页文件使用约 11.6 GiB，采样观察到大量换页，因此并行存在实际资源压力，不能声称其对耗时没有影响。

进一步检查官方 SQLite 请求缓存：235 次 EDU filter 中，200 次 `finish_reason=length` 并达到 8192 输出 token，223 次原始响应不是合法 JSON。查询实体抽取 206 次原始 JSON 全部有效。长筛选输出包含大量转义后的中文及嵌套诊疗 JSON；官方原生代码在解析错误后返回候选兜底，实验继续，但其成本与记忆质量均受影响。原始 JSON 无效数不等同于最终恢复后无效数。

单独重放一条已有请求进行格式诊断，不计入正式实验：仅 JSON 模式仍在 8192 token 截断，90.81 秒；JSON 模式加中文直接输出和正确转义要求后返回合法 `selected_edus`，5364 输出 token，54.80 秒。这只有单条诊断证据，不能证明全量修复效果。正式 EMem 流程未改，已向用户询问修复后重跑、修复后分段续跑或维持现状。请求、原响应和 usage 均保存在 `repairs/20261109-emem-latency-diagnostic`。

## Memora 第 44 例 cue 生命周期故障

第 43 例检查点中，`Patient bleeding manifestations` 已从 cue 变成 factual primary，另一个 primary 仍将此字符串列在 cue 引用中。上游允许这种提升，并在删除其他 primary 时跳过仍为 primary 的引用；但提升后的 primary 再被删除时，没有清除其他 primary 的旧引用，导致后续删除报 cue 不存在。

在适配层为单实例绑定删除生命周期清理：即将删除 primary 时，按精确 key 清除其他对象中指向它的 cue 元数据，再调用原生 delete。其余事实、向量、历史、对象身份及其他关系保留，不吞掉真正的缺失 cue 错误，不伪造索引或替换记忆算法。官方源码保持原样。

11 项 Memora 原生测试与 58 项公共回归通过；新增回归使用实际 Chroma 复现 cue 提升、删除、保留其他事实和精确向量，再删除原 primary。审计 `repairs/20261109-memora-converted-cue/repair-audit.json`，单独请求 Memora 从已提交 43 例恢复。EMem 持续运行。

## 第 47 例后公共恢复校验内存故障

第 47 例的学习和快照已提交，随后病例计量中出现 `MemoryError`。最新检查点文件达 407.45 MiB；原公共恢复选择器会同时解析并保留全部候选快照，校验哈希又生成完整 canonical 字符串及字节副本。此资源成本属于公共保障层，不能归因于原生记忆算法。并行环境的内存压力会放大其失败风险。

修复最新候选优先读取（保留 schema、提交标记、位置与哈希校验，损坏的新快照仍拒绝），SHA256 改为流式编码的完全相同 canonical 字节，保留检查点校验时提前释放上一份完整对象。原 schema、快照、结果和全部旧用量保持原样。

64 项公共回归通过，包含新旧哈希一致和仅读取最新快照的回归。实际第 47 例检查点校验通过，耗时 7.57 秒，独立进程峰值工作集 1432.02 MiB。审计为 `repairs/20261109-recovery-memory/repair-audit.json`；Memora 从 47 恢复，补缺失的病例测量点后继续第 48 例，禁止重复学习第 47 例。
