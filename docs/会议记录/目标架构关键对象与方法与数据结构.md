# 目标架构的关键对象、方法与数据结构

> 本文依据《评测主线与对象关系设计》展开，描述 MemAtlas 评测框架完成重构后的目标形态。
>
> 文中的类名、字段和伪代码是目标合同，不代表当前仓库已经全部实现。现有可复用对象会明确标注；目标新增对象需要经过兼容层逐步落地。

## 1. 先看整体：目标架构在解决什么

目标框架需要在固定 Agent、任务安排和评分条件下，公平比较多个 Memory 方法。它同时覆盖两类评测：

- 经典 Benchmark：例如 QA 数据集上的一次测试，或先导入历史再冻结测试。
- 连续 RSI：Agent 在训练任务中取得反馈并更新记忆，在多个学习点反复测试后续表现。

整条主线如下：

```text
ExperimentConfig
    │ 用户可保存的实验输入
    ▼
ExperimentSpec
    │ 已解析、冻结并校验的实验说明
    ▼
ExperimentRunner
    │ 逐个 Memory 方法创建相互隔离的运行资源
    ├─ 方法 A → Memory A → Adapter A → RunRunner A → MethodRunResult A
    ├─ 方法 B → Memory B → Adapter B → RunRunner B → MethodRunResult B
    └─ 方法 C → Memory C → Adapter C → RunRunner C → MethodRunResult C
                                                    │
                                                    ▼
                                           ExperimentResult
```

单个方法内部的时间流程如下：

```text
RunPlan
  └─ RunStep(train / boundary / test)
       │
       ▼
RunRunner
  ├─ train    → ScenarioAdapter.run_train()
  ├─ boundary → ScenarioAdapter.deliver_feedback()
  │             + Memory.learning_boundary()/flush()
  └─ test     → 可选 Memory.read_only()
                + ScenarioAdapter.run_test()
       │
       ▼
ResultStore → 进度、逐步结果、快照、恢复 → MethodRunResult
```

这里有三条最重要的职责边界：

1. `ExperimentRunner` 决定比较哪些方法，并为每种方法创建独立资源。
2. `RunRunner` 决定何时训练、何时交付反馈、何时测试，不理解患者或题目字段。
3. `ScenarioAdapter` 知道本场景怎样运行 Agent、加载任务、取得反馈和评分。

`Memory` 继续作为 Agent 与具体 Memory 方法之间的公共运行层。ExpeL、Mem0 等方法只实现记忆算法，不安排实验流程。

## 3. 实验输入层：描述一次公平比较

### 3.1 `ExperimentConfig`：用户可保存的原始配置

`ExperimentConfig` 表达“用户想运行什么实验”。它应只保存可序列化配置，不持有已经启动的 Memory、Agent、Adapter 或评分器实例。

建议字段：

```python
@dataclass(frozen=True)
class ExperimentConfig:
    methods: tuple[MemAtlasConfig, ...]
    scenario: Mapping[str, Any]
    plan: Mapping[str, Any]
    output_root: Path
    metadata: Mapping[str, Any] = field(default_factory=dict)
```

| 字段 | 含义 |
| --- | --- |
| `methods` | 需要比较的 Memory 方法配置 |
| `scenario` | 场景、Agent、数据源、评分政策和随机种子等配置 |
| `plan` | 任务安排参数，例如训练名单、重复次数、反馈边界和测试点 |
| `output_root` | 整个实验的输出根目录 |
| `metadata` | 实验名称、备注、配置版本等可追溯信息 |

关键方法：

```python
ExperimentConfig.from_dict(data) -> ExperimentConfig
config.to_dict() -> dict
load_experiment_config(path) -> ExperimentConfig
```

创建者通常是 CLI、配置文件加载器或 Python API。它的下一站是 `build_experiment_spec()`。

### 3.2 `ExperimentSpec`：已经解析并冻结的运行说明

`ExperimentSpec` 不是一次正在运行的实验实例。它是配置经过解析、任务名单冻结、能力需求确定后的不可变运行说明。

建议字段：

```python
@dataclass(frozen=True)
class ExperimentSpec:
    methods: tuple[MemAtlasConfig, ...]
    plan: RunPlan
    scenario_factory: ScenarioAdapterFactory
    output_root: Path
    condition_fingerprint: str
    metadata: Mapping[str, Any] = field(default_factory=dict)
```

关键含义：

- 所有方法共享同一份不可变 `RunPlan`。
- `scenario_factory` 保存固定场景条件，但不持有某个方法的 Memory。
- `condition_fingerprint` 覆盖固定 Agent 配置、数据名单、评分政策和随机种子，用于比较与恢复校验。
- 方法自己的存储目录和运行状态不放在 Spec 中，由 `ExperimentRunner` 为每种方法创建。

关键方法：

```python
spec.validate() -> None
spec.requirements() -> ProtocolRequirements
spec.to_manifest() -> Mapping[str, Any]
```

构建过程：

```python
def build_experiment_spec(config: ExperimentConfig) -> ExperimentSpec:
    plan = build_run_plan(config.plan, config.scenario)
    factory = build_scenario_factory(config.scenario)
    requirements = factory.requirements(plan)
    validate_all_methods(config.methods, requirements)
    return ExperimentSpec(...)
```

## 4. 计划层：只表达任务顺序，不执行任务

Plan 的作用是把“何时训练、何时交付反馈、何时测试”变成不可变数据。它不包含患者病历、题目正文、Agent 实例、Memory 状态或评分结果。

### 4.1 `TaskOccurrence`：任务在计划中的一次出现

```python
@dataclass(frozen=True)
class TaskOccurrence:
    occurrence_id: str
    case_id: str
    split: str
```

| 字段 | 含义 | OpenHospital 示例 | QA 示例 |
| --- | --- | --- | --- |
| `occurrence_id` | 本次出现的唯一身份 | `P17:visit:2` | `Q8:test:1` |
| `case_id` | 场景原始任务身份 | 患者 `P17` | 题目 `Q8` |
| `split` | 数据划分 | `train`、`primary_test` | `train`、`test` |

必须区分 `occurrence_id` 和 `case_id`。同一患者可以多次训练；同一测试患者也可以在训练前后重复测试。每次出现都需要独立身份，才能正确记录进度、结果和恢复位置。

医生在一次问诊中的多次提问仍属于同一个 occurrence 内部的 Agent 轨迹，不拆成多个 Plan 任务。

### 4.2 `RunStep`：一段需要执行的计划动作

```python
RunStepKind = Literal["train", "boundary", "test"]

@dataclass(frozen=True)
class RunStep:
    step_id: str
    kind: RunStepKind
    tasks: tuple[TaskOccurrence, ...] = ()
    train_source: Literal["agent", "history_import"] | None = None
    feedback_event: str | None = None
    learning_events: tuple[str, ...] = ()
    trigger: tuple[str, int] | None = None
    freeze_memory: bool = False
```

三种 step 的含义：

| `kind` | 做什么 | 常用字段 |
| --- | --- | --- |
| `train` | 运行训练 Agent，或导入已有历史 | `tasks`、`train_source` |
| `boundary` | 交付到期反馈，并通知方法完成批次或 epoch 学习 | `feedback_event`、`learning_events` |
| `test` | 运行留出任务并评分 | `tasks`、`trigger`、`freeze_memory` |

`trigger=("completed", 200)` 表示实际完成 200 次训练后才能测试。计数口径至少要区分：

- `scheduled`：计划安排了多少次。
- `attempted`：实际尝试了多少次。
- `completed`：Agent 成功完成多少次任务执行。
- `learned`：多少次经历已经提交给 Memory 方法学习。

失败导致触发条件暂未达到时，测试应保持“待触发”，不能记成 0 分或已完成。

### 4.3 `RunPlan`：一个方法运行时共享的完整顺序

```python
@dataclass(frozen=True)
class RunPlan:
    plan_id: str
    steps: tuple[RunStep, ...]
    failure_policy: Literal["stop", "skip"] = "stop"
```

关键方法：

```python
plan.validate() -> None
plan.steps_from(progress: RunProgress) -> tuple[RunStep, ...]
plan.to_dict() -> dict
```

`validate()` 至少检查：

- `step_id` 和 `occurrence_id` 是否唯一。
- 训练集和留出测试集是否满足规定的隔离关系。
- `train` step 是否声明 `train_source`。
- `boundary` 是否放在合法位置。
- 触发口径和目标值是否合法。
- `plan_id` 是否对应冻结后的实际安排。

一个最小医院计划：

```python
RunPlan(
    plan_id="hospital-plan-v1",
    steps=(
        RunStep(
            step_id="baseline",
            kind="test",
            tasks=(TaskOccurrence("T@0", "T", "primary_test"),),
            trigger=("completed", 0),
            freeze_memory=True,
        ),
        RunStep(
            step_id="visit-1",
            kind="train",
            tasks=(TaskOccurrence("P:visit:1", "P", "train"),),
            train_source="agent",
        ),
        RunStep(
            step_id="batch-1",
            kind="boundary",
            feedback_event="batch_end",
            learning_events=("batch_end",),
        ),
        RunStep(
            step_id="after-1",
            kind="test",
            tasks=(TaskOccurrence("T@1", "T", "primary_test"),),
            trigger=("completed", 1),
            freeze_memory=True,
        ),
    ),
)
```

## 5. 场景扩展层：把通用流程接到具体 Agent

### 5.1 `ScenarioAdapterFactory`：为每个方法创建独立场景

Factory 保存固定场景配置，并为每种 Memory 方法创建新的 Adapter。它本身不执行任务，也不持有运行中的 Memory。

```python
class ScenarioAdapterFactory(Protocol):
    def requirements(self, plan: RunPlan) -> ProtocolRequirements:
        ...

    def create(
        self,
        *,
        memory: Memory,
        output_dir: Path,
    ) -> ScenarioAdapter:
        ...
```

`requirements()` 根据场景和 Plan 声明需要哪些记忆能力，例如：

- 是否需要 `retrieve`、`observe`、`learn`。
- 需要接受哪些事件、模态和 episode 字段。
- 测试是否要求冻结 Memory。
- 是否要求保存和恢复状态。
- 需要多少个 Memory scope。

`create()` 必须使用 `ExperimentRunner` 刚为当前方法创建的同一个 `Memory`。不同方法之间不得复用有状态的 Agent、Adapter、医院会话或评分器。

### 5.2 `ScenarioAdapter`：执行本场景的一步

```python
class ScenarioAdapter(Protocol):
    async def run_train(self, step: RunStep) -> TrainStepResult:
        ...

    async def deliver_feedback(self, step: RunStep) -> FeedbackResult:
        ...

    async def run_test(self, step: RunStep) -> TestStepResult:
        ...
```

三个核心接口：

| 方法 | 输入 | 内部做什么 | 返回 |
| --- | --- | --- | --- |
| `run_train` | 一个训练 `RunStep` | 加载任务，运行 Agent 或导入历史，让 Agent 使用 Memory | `TrainStepResult` |
| `deliver_feedback` | 一个边界 `RunStep` | 取得到期反馈，更新对应 episode 状态 | `FeedbackResult` |
| `run_test` | 一个测试 `RunStep` | 加载留出任务，运行 Agent，调用场景评分 | `TestStepResult` |

可选生命周期接口：

```python
async def setup(self) -> None: ...
async def close(self) -> None: ...
def snapshot_metadata(self) -> Mapping[str, Any]: ...
def restore_metadata(self, data: Mapping[str, Any]) -> None: ...
```

无状态 QA Adapter 不需要被迫实现复杂恢复逻辑。有状态医院 Adapter 则需要保存医院 world、team、患者科室、反馈队列和病例日志引用等恢复信息。

通用 Runner 不要求所有 Agent 继承同一个基类。场景内部既可以调用 `agent(case, memory)`，也可以经医院 SDK 创建医生 Agent。

## 6. 运行器：一个管方法维度，一个管时间维度

### 6.1 `ExperimentRunner`：外层多方法比较

```python
class ExperimentRunner:
    async def evaluate(self, spec: ExperimentSpec) -> ExperimentResult:
        ...
```

它负责：

1. 写入实验条件 manifest。
2. 逐个读取 `spec.methods`。
3. 检查方法能力是否满足 `ScenarioAdapterFactory.requirements(plan)`。
4. 为当前方法创建独立输出目录和存储命名空间。
5. 创建当前方法的 `Memory`、`ScenarioAdapter` 和 `ResultStore`。
6. 调用一次 `RunRunner.run()`。
7. 收集所有 `MethodRunResult`，生成 `ExperimentResult`。

伪代码：

```python
async def evaluate(self, spec):
    experiment_id = uuid4().hex
    runs = []
    for method_config in spec.methods:
        requirements = spec.scenario_factory.requirements(spec.plan)
        check_capabilities(method_config, requirements)

        run_dir = create_isolated_run_dir(spec, method_config)
        memory = Memory(with_isolated_storage(method_config, run_dir))
        adapter = spec.scenario_factory.create(
            memory=memory,
            output_dir=run_dir,
        )
        store = ResultStore(run_dir, spec=spec, memory=memory)

        result = await RunRunner(
            plan=spec.plan,
            memory=memory,
            adapter=adapter,
            store=store,
        ).run()
        runs.append(result)

    return ExperimentResult(
        experiment_id=experiment_id,
        condition_fingerprint=spec.condition_fingerprint,
        runs=tuple(runs),
    )
```

`ExperimentRunner` 不执行患者问诊，不解析 QA 答案，也不直接调用具体 `BaseMemoryMethod`。

### 6.2 `RunRunner`：单方法的时间循环

建议构造字段：

```python
@dataclass
class RunRunner:
    plan: RunPlan
    memory: Memory
    adapter: ScenarioAdapter
    store: ResultStore
```

关键方法：

```python
async def run(self) -> MethodRunResult
async def _run_train(self, step: RunStep) -> None
async def _run_boundary(self, step: RunStep) -> None
async def _run_test(self, step: RunStep) -> None
async def _run_due_tests(self, progress: RunProgress) -> None
```

主循环：

```python
async def run(self):
    await self.memory.setup()
    await setup_if_supported(self.adapter)
    try:
        progress = await self.store.load_or_start_and_restore(
            memory=self.memory,
            adapter=self.adapter,
        )

        for step in self.plan.steps_from(progress):
            if step.kind == "train":
                result = await self.adapter.run_train(step)
                progress = await self.store.record_training(step, result)

            elif step.kind == "boundary":
                result = await self.adapter.deliver_feedback(step)
                progress = await self.store.record_feedback(step, result)
                for event in step.learning_events:
                    await self.memory.learning_boundary(event)
                await self.memory.flush()

            elif step.kind == "test":
                if not progress.trigger_reached(step.trigger):
                    progress = await self.store.defer_test(step)
                    continue
                async with read_only_if(self.memory, step.freeze_memory):
                    result = await self.adapter.run_test(step)
                progress = await self.store.record_test(step, result)

            progress = await self.store.confirm_and_snapshot(
                step, self.memory, self.adapter
            )

        return self.store.method_result()
    finally:
        await close_if_supported(self.adapter)
        await self.memory.close()
```

这里的执行顺序很重要：先记录实际结果，再原子确认进度和快照。医院若支持病例级恢复，Store 不能只保存 step 下标，还要保存已经确认的 occurrence。

## 7. Memory 层：继续复用现有公共运行时

### 7.1 `Memory`：Agent 使用记忆的统一入口

`Memory` 是现有对象，目标架构继续复用它。Runner 和 Adapter 引用的是同一个 `Memory` 实例：Runner 控制生命周期、只读和学习边界；Adapter 将它接给场景 Agent。

关键方法：

```python
await memory.setup()
await memory.retrieve(context: DecisionContext) -> MemoryContribution
await memory.recall(query, ...) -> MemoryContribution
await memory.observe(event: MemoryEvent)
memory.record_episode(episode: MemoryEpisode) -> EpisodeResult
await memory.submit_episode(episode: MemoryEpisode) -> EpisodeResult
await memory.submit_feedback(episode_id, ...) -> EpisodeResult
await memory.learning_boundary(event)
await memory.flush()
async with memory.read_only(): ...
await memory.save_state()
await memory.load_state(state)
await memory.close()
```

`Memory` 内部才调用具体方法接口：

```text
Agent / ScenarioAdapter
        │ 公共调用
        ▼
      Memory
        │ 统一检查、追踪、只读、回合组织
        ▼
BaseMemoryMethod
        │ 方法自己的算法与数据库
        ▼
ExpeL / Mem0 / 其他方法
```

### 7.2 `BaseMemoryMethod` 与 `MethodPlugin`

这两个现有对象不承担实验调度。

```python
class BaseMemoryMethod:
    async def setup(self, context: MethodContext) -> None: ...
    async def observe(self, event: MemoryEvent) -> None: ...
    async def retrieve(self, context: DecisionContext) -> MemoryContribution: ...
    async def learn(self, episode: MemoryEpisode) -> None: ...
    async def commit(self) -> None: ...
    async def save_state(self) -> Mapping[str, Any]: ...
    async def load_state(self, state: Mapping[str, Any]) -> None: ...
    async def close(self) -> None: ...
```

`MethodPlugin` 保存方法描述、能力、参数规则和创建方式；`ProtocolRequirements` 用于在运行前检查场景需要的能力是否与方法实际能力兼容。

### 7.3 一次交互中的公共数据

| 对象 | 表达什么 | 主要流向 |
| --- | --- | --- |
| `DecisionContext` | 当前 Agent 在什么上下文中需要什么记忆 | Adapter/Agent → Memory |
| `MemoryContribution` | 方法检索出的条目、上下文或其他贡献 | Memory → Agent |
| `MemoryEvent` | 一次消息、动作、工具调用或结果事件 | Agent/Bridge → Memory |
| `EpisodeOutcome` | 一次任务的成功、奖励和反馈 | 场景 → Memory |
| `MemoryEpisode` | 完整任务轨迹及其结果 | Memory → BaseMemoryMethod |
| `EpisodeResult` | 框架对执行、反馈和学习状态的记录 | Memory/Adapter → step result |

需要保持三个概念分离：

```text
MemoryContribution：这次决策拿到了哪些记忆
MemoryEpisode：本次任务发生了什么，可供方法学习什么
EpisodeResult：这次经历当前执行到什么状态
```

### 7.4 `EpisodeHistory`、`FeedbackSchedule` 与 `ProtocolRequirements`

这三个现有对象仍参与目标评测流程，但不替代 `ResultStore`：

| 对象 | 所在层 | 负责什么 | 与目标新对象的关系 |
| --- | --- | --- | --- |
| `EpisodeHistory` | Memory 运行层 | 保存 episode 最新处理状态、轨迹、待反馈和应用来源 | `TrainStepResult/FeedbackResult` 引用其中的 `EpisodeResult`；Store 将它随 Memory 状态一起恢复 |
| `FeedbackSchedule` | Memory 运行层或场景 Bridge | 决定反馈立即、批量或延迟送达 | Adapter 在 boundary 调用它交付到期反馈，Runner 不解释临床反馈内容 |
| `ProtocolRequirements` | 公共合同层 | 声明场景需要的操作、事件、模态、冻结和恢复能力 | Factory 根据 Plan 生成要求，ExperimentRunner 在创建运行资源前检查方法能力 |

`EpisodeHistory` 记录的是 Memory 回合的事实；`RunProgress` 记录的是实验计划执行到哪里。一个 episode 的状态可以因延迟反馈发生更新，因此 Store 需要读取最新 episode 状态，再更新运行进度。

`FeedbackSchedule` 决定某条反馈什么时候到期，`RunStep(kind="boundary")` 决定实验什么时候触发一次交付检查。两者分工如下：

```text
RunPlan / RunRunner：现在到 batch_end，应该检查并交付反馈
FeedbackSchedule：哪些 episode 的反馈在这个 batch_end 已经到期
ScenarioAdapter：如何取得场景反馈并映射为 reward/success/feedback
Memory：把有效反馈提交给具体记忆方法
```

## 8. step 结果：把执行事实传回 Runner

### 8.1 `TrainStepResult`

```python
@dataclass(frozen=True)
class TrainStepResult:
    step_id: str
    episodes: tuple[EpisodeResult, ...] = ()
    imports: tuple[HistoryImportResult, ...] = ()
    metrics: Mapping[str, Any] = field(default_factory=dict)
    artifacts: Mapping[str, str] = field(default_factory=dict)
```

它表达训练 step 实际发生了什么：

- `train_source="agent"` 时，每个 occurrence 应对应一个 `EpisodeResult`。
- `train_source="history_import"` 时，返回独立的历史导入记录，不伪装成 Agent 完成了一次任务。
- `metrics` 保存本 step 的场景指标或资源差分。
- `artifacts` 只保存产物引用，不把大段原始日志塞进结果对象。

`HistoryImportResult` 的具体字段需要在 QA 迁移时结合现有协议确定；至少要能表达导入身份、成功状态、错误和关联 occurrence。

### 8.2 `FeedbackResult`

```python
@dataclass(frozen=True)
class FeedbackResult:
    step_id: str
    episodes: tuple[EpisodeResult, ...]
    pending_count: int
    metrics: Mapping[str, Any] = field(default_factory=dict)
```

反馈可能把某个 episode 从：

```text
feedback=pending, learning=pending
```

更新为：

```text
feedback=valid, learning=submitted
```

因此 Store 应按 `episode_id` 覆盖这条 episode 的最新状态，不能把训练结果和反馈结果累计成两次经历。

### 8.3 `TestStepResult`

```python
@dataclass(frozen=True)
class TestStepResult:
    step_id: str
    cases: tuple[TestCaseResult, ...]
    native_metrics: Mapping[str, Any]
    common_metrics: Mapping[str, Any] = field(default_factory=dict)
    artifacts: Mapping[str, str] = field(default_factory=dict)
```

它保存逐任务输出或评分引用、场景原生指标、公共覆盖率和资源指标。测试评分只进入评测报告，不自动转成训练反馈提交给 Memory。

医院和 QA 不需要使用相同的原生评分字段：

```text
OpenHospital native_metrics：诊断、检查、治疗等官方指标
QA native_metrics：准确率、F1、检索指标或 judge 分数
```

`TestCaseResult` 的最小公共字段建议是 `occurrence_id`、`case_id`、执行状态、输出引用、评分引用和错误；场景完整报告继续保存在场景产物中。

## 9. 进度、存储与恢复

### 9.1 `RunProgress`：已发生事实的运行游标

```python
@dataclass(frozen=True)
class RunProgress:
    confirmed_step_ids: tuple[str, ...]
    confirmed_occurrence_ids: tuple[str, ...]
    attempted: int
    completed: int
    learned: int
    failed: int
    pending_feedback: int
    deferred_test_ids: tuple[str, ...]
    snapshot_id: str | None
    usage_cursor: Mapping[str, Any]
```

`RunPlan` 表示计划；`RunProgress` 表示实际执行事实。二者不能合并，否则失败、跳过、延迟反馈和中断恢复都会变得含糊。

计数应从 episode 最新状态或已确认记录推导，不能只依靠循环下标。具体是否把全部字段直接保存，还是从事件日志计算，属于实现阶段的选择。

### 9.2 `ResultStore`：当前方法的运行账本

```python
class ResultStore:
    async def load_or_start_and_restore(
        self, *, memory: Memory, adapter: ScenarioAdapter
    ) -> RunProgress: ...

    async def record_training(
        self, step: RunStep, result: TrainStepResult
    ) -> RunProgress: ...

    async def record_feedback(
        self, step: RunStep, result: FeedbackResult
    ) -> RunProgress: ...

    async def record_test(
        self, step: RunStep, result: TestStepResult
    ) -> RunProgress: ...

    async def defer_test(self, step: RunStep) -> RunProgress: ...

    async def confirm_and_snapshot(
        self,
        step: RunStep,
        memory: Memory,
        adapter: ScenarioAdapter,
    ) -> RunProgress: ...

    def method_result(self) -> MethodRunResult: ...
```

它负责保存：

- 每个 step 与 occurrence 的最新结果。
- 公共用量、资源差分和错误。
- Memory 方法状态与公共 episode history。
- Adapter 提供的场景恢复元数据。
- Plan、实验条件和代码版本的校验信息。
- 产物文件路径和快照清单。

它不保存供 Agent 检索的长期知识库内容；知识库仍归具体 Memory 方法管理。Store 保存的是实验记录和恢复材料。

恢复时至少校验：

- `plan_id`、方法 ID 和方法配置是否一致。
- 固定 Agent、数据、评分政策和随机种子是否一致。
- Memory 状态、episode history 和 Adapter 元数据是否属于同一确认点。
- 已确认 occurrence 与场景病例日志是否相符。
- 用量账本是否能从原游标继续。

## 10. 方法级与实验级结果

### 10.1 `MethodRunResult`

```python
@dataclass(frozen=True)
class MethodRunResult:
    method_id: str
    run_id: str
    plan_id: str
    status: Literal["completed", "failed", "partial"]
    progress: RunProgress
    step_results: tuple[Mapping[str, Any], ...]
    metrics: Mapping[str, Any]
    resources: Mapping[str, Any]
    failures: tuple[Mapping[str, Any], ...]
    artifacts: Mapping[str, str]
```

它表示一个 Memory 方法在完整公共计划上的结果。学习曲线、失败位置、资源开销和逐 step 产物都应能追溯到这个对象。

### 10.2 `ExperimentResult`

```python
@dataclass(frozen=True)
class ExperimentResult:
    experiment_id: str
    condition_fingerprint: str
    runs: tuple[MethodRunResult, ...]

    def to_dict(self) -> dict: ...
```

它只汇总同一实验条件下的多个方法结果。报告层据此生成比较表或曲线，不在结果对象中重新执行评分。

公平比较要求：

- 所有方法使用相同 `RunPlan`。
- Agent 配置、场景数据、评分规则和随机种子相同。
- 每种方法拥有独立 Memory、Adapter、会话和输出目录。
- 方法需要的模型服务可以不同，但其配置和资源开销必须被记录。

## 11. OpenHospital 如何实现这些接口

### 11.1 `HospitalAdapterFactory`

建议持有：

```python
@dataclass(frozen=True)
class HospitalAdapterFactory:
    doctor_config: Mapping[str, Any]
    hospital_urls: Mapping[str, str]
    patient_source: PatientSourceConfig
    scoring_policy: Mapping[str, Any]
    feedback_policy: Mapping[str, Any]
    seed: int
```

关键方法：

```python
def requirements(self, plan: RunPlan) -> ProtocolRequirements
def create(self, *, memory: Memory, output_dir: Path) -> OpenHospitalAdapter
```

`create()` 组装当前方法专属的：

```text
Memory
  ↓
OpenHospitalMemoryIntegration（Bridge）
  ↓
医生 Agent + 医院 SDK + 医院服务
  ↓
OpenHospitalAdapter
```

### 11.2 `OpenHospitalAdapter`

建议持有：

- 当前方法的 `Memory` 与医院 Bridge。
- 医生类和医生配置。
- 医院 SDK 运行配置与服务地址。
- 患者、科室和医院 world 信息。
- 官方评分与反馈策略。
- 病例日志、用量与恢复目录。

接口映射：

```python
async def run_train(self, step):
    # 按 occurrence 加载患者
    # 创建 doctor agent(config, memory=bridge)
    # 调用 hospital_agent_sdk.run_train_async(...)
    # Bridge 在问诊中执行 retrieve/confirm_application/learn_case
    # 返回每个 occurrence 最新 EpisodeResult
    return TrainStepResult(...)

async def deliver_feedback(self, step):
    # 按 feedback_event 交付到期评分或反思
    # 更新原 episode 的 feedback/learning 状态
    return FeedbackResult(...)

async def run_test(self, step):
    # 调用 hospital_agent_sdk.run_test_async(...)
    # 取得医生最终结果并调用医院官方评分
    # 测试评分不提交训练反馈
    return TestStepResult(...)
```

迁移时有一个必须注意的现状：当前 `HospitalExecution.train_batch()` 已在函数末尾交付反馈。第一阶段 Adapter 应包装现有顺序；在真正拆出 `deliver_feedback()` 前，boundary 不能再次交付，避免同一反馈被处理两次。

### 11.3 `OpenHospitalMemoryIntegration`

Bridge 继续负责把医院语义映射到公共 Memory：

```text
医生 retrieve(patient_id, phase, chat_history, examinations)
    → DecisionContext
    → Memory.recall()
    → 选择并暂存 MemoryContribution

医生 confirm_application(patient_id, phase)
    → 确认真正进入决策提示词的来源

问诊结束 learn_case(...)
    → MemoryEvent + EpisodeOutcome
    → MemoryEpisode
    → record/submit/延迟反馈流程
```

它不应决定何时进入下一个训练批次或测试点，这属于 `RunPlan` 和 `RunRunner`。

## 12. QA 如何实现同一合同

### 12.1 `QAAdapterFactory`

建议持有题库配置、answerer/Agent 配置、评分协议、随机种子和现有 QA protocol 的兼容配置。

```python
class QAAdapterFactory:
    def requirements(self, plan: RunPlan) -> ProtocolRequirements: ...
    def create(self, *, memory: Memory, output_dir: Path) -> QAAdapter: ...
```

### 12.2 `QAAdapter`

```python
async def run_train(self, step):
    if step.train_source == "history_import":
        # 将题目附带历史导入 Memory，并返回 HistoryImportResult
        ...
    else:
        # 运行训练 Agent，形成 episode
        ...

async def deliver_feedback(self, step):
    # 没有延迟反馈时返回空更新
    return FeedbackResult(step.step_id, episodes=(), pending_count=0)

async def run_test(self, step):
    # 按 case_id 加载 BenchmarkCase
    # 调用原 QA 协议或 agent(case, memory)
    # 先收集逐题输出，再调用 Benchmark 原生评分
    return TestStepResult(...)
```

两类现有 QA 语义都要保留：

- Streaming：测试过程中可能导入该题历史并更新 Memory，对应 `freeze_memory=False`。
- 训练后冻结测试：先通过训练 step 导入历史，再在测试 step 使用 `freeze_memory=True`。

Plan 必须明确这一区别，不能默认所有测试都会冻结 Memory。

## 13. 从配置到结果的完整传参关系

| 顺序 | 创建者 → 接收者 | 传什么 | 返回什么 |
| --- | --- | --- | --- |
| 1 | CLI → Spec 构建器 | `ExperimentConfig` | `ExperimentSpec` |
| 2 | Spec 构建器 → Plan 构建器 | 计划参数、冻结任务名单 | `RunPlan` |
| 3 | Spec 构建器 → Factory 构建器 | 场景、Agent、评分配置 | `ScenarioAdapterFactory` |
| 4 | `ExperimentRunner` → `Memory` | 当前方法配置和独立工作区 | 当前方法的 `Memory` |
| 5 | `ExperimentRunner` → Factory | 同一个 `Memory`、当前方法输出目录 | 新的 `ScenarioAdapter` |
| 6 | `ExperimentRunner` → `RunRunner` | `plan + memory + adapter + store` | `MethodRunResult` |
| 7 | `RunRunner` → Adapter | 当前 `RunStep` | 对应 step result |
| 8 | Adapter → Agent/SDK | 场景任务及同一个 Memory/Bridge | Agent 原始执行结果 |
| 9 | Agent/Bridge → Memory | Context、Event、Episode | Contribution、EpisodeResult |
| 10 | Adapter → 场景评分器 | Agent 输出和参考信息 | 原生评分 |
| 11 | `RunRunner` → Store | step 结果、Memory 和场景恢复状态 | 新 `RunProgress` |
| 12 | `ExperimentRunner` → 报告层 | `ExperimentResult` | JSON、比较表、曲线 |

## 14. 一个完整 OpenHospital 例子

假设比较 Mem0 和 ExpeL，计划包含训练前测试、一次训练问诊、反馈边界和训练后测试：

```python
config = ExperimentConfig(
    methods=(mem0_config, expel_config),
    scenario=hospital_scenario_config,
    plan=hospital_plan_config,
    output_root=output_root,
)

spec = build_experiment_spec(config)
result = await ExperimentRunner().evaluate(spec)
```

对 Mem0：

```text
ExperimentRunner
  ├─ 创建 Memory(Mem0)
  ├─ Factory 创建 HospitalAdapter(Memory(Mem0))
  ├─ 创建 ResultStore(mem0_run_dir)
  └─ RunRunner.run()
       ├─ baseline test
       │    └─ read_only → 医生测试 → 官方评分
       ├─ train P:visit:1
       │    └─ 医生多轮问诊 ↔ Bridge ↔ Memory(Mem0)
       ├─ boundary batch_end
       │    └─ 交付反馈 → Mem0 学习边界 → flush
       └─ after-1 test
            └─ read_only → 医生测试 → 官方评分
```

然后 ExperimentRunner 为 ExpeL 重新创建完全独立的 Memory、Adapter、Store，在同一个 `RunPlan` 上运行。最后两个 `MethodRunResult` 汇总为一个 `ExperimentResult`。

## 17. 与当前实现的关系和迁移原则

当前已有并应优先复用：

- `Memory`、`BaseMemoryMethod`、`MethodPlugin` 和 `ProtocolRequirements`。
- `DecisionContext`、`MemoryContribution`、`MemoryEpisode` 和 `EpisodeResult`。
- episode history、延迟反馈、只读范围、方法状态保存与用量记录。
- 现有 QA protocol、Benchmark 原生评分和 OpenHospital Bridge/Execution。

目标新增或需要收拢：

- 统一的 `RunPlan/RunStep/TaskOccurrence`。
- `ScenarioAdapterFactory/ScenarioAdapter` 最小接口。
- 单方法 `RunRunner` 与真正承担多方法循环的 `ExperimentRunner`。
- step 结果、`RunProgress`、`ResultStore`、`MethodRunResult` 和统一 `ExperimentResult`。

建议迁移顺序：

1. 固定现有 QA 和医院的执行、评分、反馈、冻结与恢复行为，建立无模型的小规模回归样例。
2. 新增 Plan 数据结构，以及现有 `ExperiencePlan/ExperienceStreamPlan` 到 `RunPlan` 的转换。
3. 用 Adapter 包装现有 QA protocol 和 `HospitalExecution`，先保持原调用顺序。
4. 引入 `RunRunner`，让两条路径逐步使用同一时间循环。
5. 将多方法循环收拢到 `ExperimentRunner`。
6. 行为等价得到验证后，再合并日志、快照和旧 Runner，保留旧结果与快照读取兼容。

## 18. 仍需在实现前确认的合同

以下内容在目标主线中已明确存在，但具体字段或实现方式还需结合现有代码验证：

1. `HistoryImportResult` 和 `TestCaseResult` 的最终最小字段。
2. 病例级恢复采用一致快照，还是使用经过验证的幂等日志重放。
3. 医院评分、医生配置、医院 world 和多方法会话隔离如何形成统一条件指纹。
4. QA 各协议哪些操作会在测试阶段更新 Memory，以及对应的恢复记录方式。
5. `RunProgress` 使用直接持久化字段，还是以追加事件日志为真值后计算得到。
6. 旧 `ExperiencePlan`、`ExperienceRunner` 和现有实验结果格式需要保持兼容的版本周期。

这些待确认项不会改变“ExperimentRunner 管方法、RunRunner 管时序、Adapter 管场景、Memory 管记忆方法”的主关系，但会影响恢复格式和第一阶段兼容层的实现。
