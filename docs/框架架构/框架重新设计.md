# RiseMem 框架重新设计讨论

创建日期：2026-10-12。更新日期：2026-11-01。

本文持续记录本轮架构讨论的目标、议题和已确认结论。未确认的方案先在对话中讨论，确认后再更新对应章节，重要设计调整简要保留原因。

## 1. 本轮目标与基础

RiseMem 是面向 MemoryRSI 的记忆方法集成、比较与实证测评项目，沿 `from RSI-inert to RSI-enabling` 组织研究，并配套可使用的工具箱。架构设计服务于方法接入、可信比较和研究证据；论文贡献仍需结合分析与实验确定。

当前聚焦任务 0：提高框架质量，使代码逻辑、职责解耦、使用方式和文件组织清晰。项目此前随需求多次迭代，本轮先系统审定设计，再对照现有代码确定保留、简化和重构范围。

当前阶段已进入代码落地与持续核对。当前源码基线：内层仓库分支 `refactor/rsi-evaluation`，提交 `7597c34`。此前原始讨论见同目录的 `原始对话记录.md`；历史记录中的代码状态以当前源码和 Git 为准。

已明确的基础：

1. 通用层处理记忆操作和回合公共规则；场景层适配 Agent 与环境；实验层调度多个回合并开展评测。当前代码已按此划分主要入口，层间职责仍在收拢。
2. 一次交互回合可以包含多次记忆操作。同一个 Memory 串行服务多个回合，长期记忆持续保留，各回合的局部记录独立。
3. Benchmark 负责数据与原生评分，Evaluation 负责评测与调度，公共数据层保存通用输入输出，医院模块负责医生与医院服务的映射，启动脚本负责读取配置与启动。
4. 各记忆方法保留自己的算法、数据库和原生更新时机。具体能力与实现差异需要清楚说明。

## 2. 讨论方式与设计顺序

本轮先采用概念架构梳理功能、职责和协作关系，再以现有代码核对对象、接口与模块边界。当前架构主线已经落入代码，后续按职责审查和实现进度迭代。

| 顺序 | 设计内容 | 需要明确的问题 |
|---|---|---|
| 1 | 核心能力与使用流程（已明确） | 共性接口、特有接口及各方法与 Benchmark 的使用条件，见第 3—5 节 |
| 2 | 概念架构：功能分解与模块划分（已形成，持续核对） | 通用层、场景层和实验层的职责及协作边界 |
| 3 | 核心对象、方法与数据结构（已实现，持续精简） | 公共数据如何流转与保存，方法特有数据放在哪里 |
| 4 | 公共接口与扩展方式（已实现，方法迁移中） | Agent 如何使用统一接口，新方法如何声明能力和必要差异 |
| 5 | 状态与生命周期规则（已实现，场景验收中） | 记录、反馈、学习、冻结、失败和恢复的边界 |
| 6 | 配置与运行记录（已实现，持续完善） | 参数检查，以及轨迹、结果和资源信息的关联 |

上述设计已映射到当前目录和公共入口；后续调整需对应实际职责、行为或验收缺口。

## 3. 已明确：核心能力与使用流程

1. **独立接入 Agent。**选择方法并配置、检查后使用；在交互中按需请求记忆、提供经历与反馈，按方法原生规则更新，供后续回合复用。
2. **按稳定约定接入与切换。**`observe`、`retrieve`、`learn` 对用户有固定用途和调用时机；方法内部处理算法与更新差异。切换方法时优先保留原有调用位置，必要时按清单补充数据或作少量接入调整。——10.31
3. **接入与扩展。**支持研究者添加自己的记忆方法、Agent、场景和评测指标；各方法保留自己的算法、数据库和特有功能。
4. **方法比较与评测。**支持经典 Benchmark 和自定义评测，在明确的输入与执行条件下比较方法，记录效果、资源成本和实现差异。
5. **连续学习与 RSI 测评。**同一份长期记忆服务多个串行回合，按计划安排反馈和冻结评测，观察学习、复用与退化，支持检查点和恢复。
6. **使用说明与辅助配置。**每个 Memory 方法和 Benchmark 提供简洁的参数、可调用接口与使用条件清单；不满足必要条件时阻止运行。支持自然语言需求解析、候选推荐和配置生成。

## 4. 已确认：共性接口与特有接口

公共接口的用途保持固定：交互事件发生时调用 `observe`，需要记忆时调用 `retrieve`，学习单元完成时调用 `learn`。各方法负责在内部实现这套约定，并保留原有算法、存储和更新时机。方法可要求不同配置、数据或少量接入调整；切换时尽量沿用原有调用位置。——10.31

`evolve` 只用于需要 Agent 主动触发演化的方法；方法能够根据自身条件自动演化时，由方法内部处理。特有接口只在公共接口和数据无法承载方法核心操作时增加，并说明必要性。`flush` 按方法要求处理待提交缓冲，不是每次 `observe` 后的统一步骤。

1. **内部实现自由。**方法自行组织算法、辅助函数、数据结构和执行顺序。框架提供输入、反馈与运行边界；必要适配应披露对原方法的改变。
2. **共同能力有明确语义。**公共接口表达信息输入、记忆请求、反馈提交和必要状态操作。方法声明实际支持的能力，框架检查调用场景能否满足其输入与执行要求。
3. **特有能力按需开放。**内部功能留在方法包；需要外部调用的功能通过明确扩展入口提供。扩展需要说明输入、输出、持久状态影响、冻结期间的使用条件及资源记录方式。
4. **按使用条件接入。**方法声明实际支持的接口及必需调用步骤，用户按要求提供参数、输入与反馈。切换方法可能需要修改配置、调用流程或 Agent 适配；不要求所有方法遵循完全相同的调用流程。

当前源码的 `Memory.command(name, payload)` 可作为扩展机制的参考。是否沿用、怎样描述与校验扩展能力，属于待设计内容。

## 5. 已确认：方法与 Benchmark 的使用清单和检查

每个 Memory 方法和 Benchmark 都应提供面向使用者的简洁清单，使用户能够据此配置与接入。具体编写要求分别集中在[方法集成任务](../方法集成/项目任务与进展.md)和[测评任务](../测评/项目任务与进展.md)。——10.30

使用前检查 Memory、Agent、Benchmark 与评测流程的必要条件。缺少必需参数、输入、反馈、接口或运行能力时，阻止该组合启动，说明缺失项与补齐方式。仅检查本次使用路径需要的能力；运行中才能确定的条件，在相关操作执行前检查。检查机制归入[框架架构任务](项目任务与进展.md)。——10.30

当前已有方法描述、配置和能力检查；逐方法与 Benchmark 的用户清单、迁移状态和检查覆盖仍需逐项补齐。本节记录设计要求，不表示这些工作已全部完成。

## 6. 当前实现与后续重点

当前主要入口：

1. Agent 通过 `Memory` 调用统一记忆接口，公共运行时记录事件、经历、反馈和运行状态。
2. 普通 Benchmark 与 OpenHospital 共用 `ExperimentConfig` 和 `ExperimentRunner`；连续学习调度由内部 `_ExperienceRunner` 承担。
3. OpenHospital 由场景适配器连接医生与医院环境；医院执行代码仍负责部分训练批次及反馈边界判断，三层职责尚未完全收拢。

后续重点是完成其余方法的 Memory v2 迁移，补齐方法与 Benchmark 的使用清单和条件检查，并核对通用层、场景层和实验层的职责边界。
