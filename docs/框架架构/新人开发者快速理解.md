# RiseMem 新人开发者快速理解

更新：2026-11-01

## 引言：先建立正确的认识

RiseMem 是集成和研究 Memory 方法的工具箱。它让不同记忆方法能以清楚的接口接入 Agent，也支持 Benchmark 比较和连续学习实验。

系统里有三类参与者：

1. **Agent** 负责对话、模型调用、工具执行和业务决策。
2. **Memory 方法** 负责记忆算法、存储和自身的更新规则。
3. **RiseMem** 在两者之间提供公共接口、运行状态管理和实验调度。

理解项目时先沿一条主线看：**Agent 把事件和学习数据交给 `Memory`，`Memory` 检查并调用具体方法；评测层使用相同的 `Memory` 接口组织多个回合并记录结果。**

## 1. 系统由哪些部分组成

```text
Agent
  ├─ observe(event)：上报交互事件
  ├─ retrieve(query)：需要记忆时检索
  ├─ 自行调用模型、工具并作业务决策
  └─ learn(episode)：提交一个完成的学习单元
             │
             ▼
       Memory 运行时
  检查输入和能力、保存公共历史、调用具体方法、管理状态
             │
             ▼
       Memory 方法
  自己实现算法、存储、即时或延迟写入、批次更新等规则

ExperimentConfig → ExperimentRunner.check() / evaluate()
  ├─ 普通 Benchmark → _EvaluationRun → DefaultQA 或用户 Agent
  └─ OpenHospitalScene → HospitalExecution → 医生与医院环境
             └─ 连续学习和检查点由内部 _ExperienceRunner 调度
                         ↓
                EvaluationResult → ExperimentRunner.results()
```

主要目录对应这些职责：

| 目录 | 负责什么 |
|---|---|
| `core/` | 公共数据、配置、方法契约、能力声明、插件注册与评测结果类型 |
| `runtime/` | `Memory` 公共运行时、历史记录、能力边界、运行隔离和方法执行器 |
| `methods/` | 各种 Memory 方法的算法适配、配置清单和原生存储 |
| `benchmarks/` | 数据集读取、案例转换和数据集原生评分 |
| `evaluation/` | `ExperimentConfig`、`ExperimentRunner`、案例执行、连续学习调度、结果与报告 |
| `integrations/openhospital/` | 医院场景适配、病例计划、医生执行、临床反馈与结果映射 |
| `providers/` | Memory 方法使用的模型和 Embedding 服务 |

## 2. 一次记忆交互如何运行

假设 Agent 要回答一个运维问题，主线如下：

```text
创建配置并检查方法条件
       ↓
创建 Memory，分配独立运行目录
       ↓
收到用户问题 ── observe(MemoryEvent)
       ↓
需要历史经验 ── retrieve(query) ── MemoryContribution
       ↓
Agent 自行组织上下文、调用模型或工具
       ↓
产生的回复和工具结果 ── observe(MemoryEvent)
       ↓
学习单元完成 ── learn(MemoryEpisode)
       ↓
若方法需要 Agent 主动触发演化，再按其规则调用 evolve()
```

示例：

```python
from uuid import uuid4
from mematlas import Memory, MemoryEvent, MemoryEpisode


async def answer(question, agent_call, config):
    report = Memory.check(config)
    if not report["ready"]:
        raise RuntimeError(report)

    async with Memory(config) as memory:
        episode_id = uuid4().hex
        await memory.observe(MemoryEvent(
            kind="message", role="user", content=question, episode_id=episode_id,
        ))

        contribution = await memory.retrieve(question, top_k=3)
        response = await agent_call(question, contribution)

        await memory.observe(MemoryEvent(
            kind="message", role="assistant", content=response, episode_id=episode_id,
        ))
        await memory.learn(MemoryEpisode(
            episode_id=episode_id,
            task=question,
            output=response,
            applied_memory=[contribution],
            # 方法需要时，按方法清单传入真实反馈和扩展字段。
        ))
        return response
```

`observe`、`retrieve`、`learn` 的用途对用户保持一致。方法内部可以采用不同算法和更新时机；换方法时，调用位置尽量保留，必要时按方法清单补充数据或少量调整接入。

## 3. 先掌握这几种数据

这些类型在 Agent、运行时和 Memory 方法之间传递信息，定义主要位于 `core/models.py` 和 `core/scope.py`。

| 类型 | 用途 | 需要记住的内容 |
|---|---|---|
| `MemoryEvent` | 一条真实交互事件 | `kind`、`content`；消息可带 `role`，事件可关联 `episode_id`；ID 和时间默认生成 |
| `MemoryContribution` | 一次检索结果 | `items` 保存记忆条目，`context` 保存整理后的内容，`extensions` 保存方法相关数据 |
| `MemoryEpisode` | 提交给方法学习的一个学习单元 | `episode_id`、事件、任务、输出、真实反馈、实际使用的 `applied_memory` |
| `EpisodeResult` | 框架记录处理状态 | 分开表示执行、反馈和学习是否完成 |
| `Scope` | 记忆的归属范围 | 配置中的字典，例如 `{"user_id": "alice"}` |

`MemoryEpisode` 的粒度由学习内容和方法要求决定，可以是一份资料、一轮交互或一段任务经历。事件既可以随 `MemoryEpisode.events` 一起提交，也可以先逐条 `observe`。后一种情况若 `learn` 省略 `events`、需要公共层从历史关联事件，`MemoryEvent` 与 `MemoryEpisode` 必须显式使用同一个 `episode_id`；框架不会自动关联“当前回合”。

内容类型 `Content` 支持文本或带类型的内容块。方法声明自己支持的模态；不支持的事件、字段或作用域会在公共边界检查时被拒绝。方法特有的数据放在方法说明要求的位置，通常通过 `extensions` 承载。

## 4. `Memory` 做什么，方法插件做什么

Agent 主要使用 `Memory`，入口定义在 `runtime/memory.py`：

| 接口 | 用途 |
|---|---|
| `Memory.check(config)` | 检查配置、依赖、服务和方法条件 |
| `Memory(config)` / `async with Memory(config)` | 创建并管理一次方法运行 |
| `observe(event)` | 保存事件，并调用方法的观察处理 |
| `retrieve(query, ...)` | 检索并返回 `MemoryContribution` |
| `learn(episode)` | 校验并提交学习单元，返回 `EpisodeResult` |
| `evolve(...)` | 仅供需要外部主动触发演化的方法使用；能够自行判断时由方法内部处理 |
| `flush()` | 方法有待处理缓冲且要求提交时使用；无需在每次操作后调用 |
| `save(path)` / `load(path)` | 保存和恢复方法状态与公共历史 |
| `read_only()` | 冻结记忆更新，用于只读执行或评测 |
| `reset(scope=...)` / `stats()` | 清理一个作用域 / 查看运行状态和用量 |

方法通过 `BaseMemoryMethod` 实现方法侧操作。公共层记录原始事件和经历、检查能力与输入、管理作用域和冻结边界，再把数据交给方法。方法决定如何从事件或学习单元中形成记忆。

### `MethodDescriptor` 和 `MethodPlugin`

它们是框架接入对象，Agent 用户不直接创建或调用。

| 对象 | 作用 | 谁会用到 |
|---|---|---|
| `MethodDescriptor` | 声明方法支持的操作、模态、事件、字段、依赖、存储、冻结能力和命令 | 注册、配置检查、能力检查、方法目录展示 |
| `MethodPlugin` | 创建具体方法，并检查配置、额外输入和运行依赖 | 插件注册、执行器和 `Memory` 初始化 |
| `BaseMemoryMethod` | 具体算法对运行时实现的接口 | Memory 方法开发者 |

常见接入关系：

```text
methods/<方法>/method.yaml
       ↓ 读取声明
MethodDescriptor ← MethodPlugin → 创建 BaseMemoryMethod
       ↓                                  ↑
PluginRegistry 找到插件 → MethodExecutor 创建运行实例
                         ↓
                  Memory 调用方法接口
```

方法的用户说明通过包入口、配置类和最小示例提供；`method.yaml` 声明方法能力、参数与运行条件，供目录和校验使用。当前 Mem0、MemRL、MemoryOS 声明 Memory v2；其他 11 个具名方法和 4 个控制基线待迁移，目录可发现不代表当前可执行。

执行器有三种：`in_process` 在当前进程运行，`subprocess` 在子进程运行，`service` 通过 HTTP 请求远程方法。除非修改执行隔离本身，新方法开发通常不需要实现新的执行器。

## 5. 评测如何复用通用运行时

评测组织多个记忆操作和回合；单次记忆操作仍由 `Memory` 完成。

| 部件 | 责任 |
|---|---|
| Benchmark | 加载案例并提供原生评分 |
| `BenchmarkCase` | 保存案例 ID、查询、历史、参考答案、作用域和可选经历 |
| `Prediction` | 保存案例输出、参考答案和实际使用的记忆贡献 |
| `EvaluationResult` | 汇总预测、指标、资源、失败和运行信息 |
| `ExperimentConfig` | 配置方法、Benchmark、协议、检查点和输出目录 |
| `ExperimentRunner` | 提供统一的 `check()`、`evaluate()` 和 `results()` 入口 |
| `_EvaluationRun`、`_ExperienceRunner` | 内部执行案例、连续学习批次、检查点、冻结测试与恢复；用户无需构造 |

关系如下：

```text
ExperimentConfig → ExperimentRunner
                      ├─ Benchmark → 默认 QA 或用户 Agent → Memory
                      └─ OpenHospitalScene → 医院医生与环境 → Memory
                              ↓
                内部执行器与评分 → EvaluationResult
```

Benchmark 负责数据和原生评分；`ExperimentRunner` 负责检查、执行和结果读取。连续学习计划与调度属于内部实现。冻结检查点测量既有记忆效果，不自动触发 `evolve()`。

## 6. 新人修改时从哪里开始

先根据改动目标找所属层，不要从目录名猜调用关系：

| 要改的内容 | 从这些文件开始 |
|---|---|
| 公共事件、经历或检索输出格式 | `core/models.py`、`runtime/history.py` |
| Agent 使用的公共调用和状态行为 | `runtime/memory.py`、`runtime/contract.py` |
| 方法能力、配置或输入校验 | `core/capabilities.py`、`core/plugin.py`、方法目录中的 `method.yaml` |
| 新增或调整 Memory 方法 | `methods/<方法>/`、`core/registry.py`、`test/` 或 `tests/` 中对应测试 |
| Benchmark 数据和原生评分 | `benchmarks/`、`core/evaluation.py` |
| 统一测评配置与入口 | `evaluation/experiment.py`、`evaluation/scenes.py` |
| 案例执行、连续学习与检查点 | `evaluation/execution.py`、`evaluation/experience.py`、`evaluation/experience_memory.py` |
| OpenHospital 场景适配 | `integrations/openhospital/` |
| 命令行或方法查询 | `cli/`、`api.py`、`catalog.py` |

### 新增 Memory 方法

1. 阅读 `BaseMemoryMethod`、`MethodPlugin` 和已有相近方法。
2. 在 `methods/<方法>/` 实现算法适配和原生状态管理。
3. 声明 `method.yaml` 中的能力、参数、依赖和限制；通过包入口、配置类和最小示例说明用户用法。
4. 确认注册方式，再补充方法核心行为、持久化、作用域及失败边界的测试。
5. 用公共 Agent 流程验证 `observe`、`retrieve`、`learn`；方法确有独立演化机制时再验证 `evolve`。

### 修改公共接口或数据

先确认已有对象无法表达什么，再修改公共模型和运行时检查；随后更新受影响的方法、Benchmark、`ExperimentRunner` 场景适配、OpenHospital 和测试。评测专用的结果、进度、反馈和恢复数据仍按其用途保留。

### 新增 Benchmark 或协议

Benchmark 实现案例读取和原生评分；通过 `ExperimentConfig` 选择实验安排，`ExperimentRunner` 统一检查、执行和汇总。已有 Agent 通过 `agent(case, memory) -> MemoryEpisode` 接入；内置问答使用 `answer_model` 和默认 QA。把数据集特有逻辑留在 Benchmark，把场景交互留在场景适配器。

## 7. 开发时要守住的约定

1. 公共接口对用户有固定用途：交互事件调用 `observe`，需要记忆时调用 `retrieve`，学习单元完成后调用 `learn`。方法内部处理可以不同。
2. 切换方法时优先保留 Agent 原有调用位置；方法要求的数据、反馈或事件类型可按清单补充，必要时允许少量接入调整。
3. 只有现有公共接口和数据无法承载方法核心操作时，才增加特有接口，并说明原因。
4. 自动演化由方法内部触发；只有确需外部主动触发的方法才声明支持 `evolve`。它不用于准备冻结评测，也不要求所有方法支持。
5. `flush` 只在方法要求处理缓冲时调用；它不代表统一的学习边界。
6. 冻结执行通过 `read_only()` 约束记忆更新。学习批次、epoch 和方法自身演化遵循方法原生规则。
7. 同一个 `Memory` 可以串行服务多个学习单元；每份学习单元有自己的 `episode_id`。ID 默认生成；若需把先前 `observe` 的事件并入省略 `events` 的 `learn`，调用方需显式复用该 ID。

## 8. 提交改动前的检查

```text
[ ] 改动放在职责所属的层
[ ] 公共数据没有重复表达同一含义
[ ] observe / retrieve / learn 的用途仍清楚
[ ] 新增特有接口确实承载方法核心操作
[ ] 方法说明、Benchmark 或场景适配已同步（按影响范围）
[ ] 相关测试覆盖成功路径和重要边界
[ ] Git 操作在 src/mematlas 内层仓库完成
```

若需要快速跟进一段调用，按此顺序阅读：`core/models.py` → `core/plugin.py` → `runtime/memory.py` → `runtime/history.py` → `evaluation/experiment.py` → `evaluation/execution.py`。理解公共路径后，再进入具体的 `methods/<方法>/` 或 `integrations/openhospital/` 场景代码。
