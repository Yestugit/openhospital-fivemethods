
**这套公共入口基本够用，但需要把 `learn` 的含义说准确：它接收完整经历，用于形成或更新记忆；反馈是否必填，由具体方法决定。**下面按我们正在讨论的目标设计说明。

**1. 在一次 Agent 执行回合中，主要会调用哪些接口？**

| 回合中的需要 | 使用接口 | 什么时候调用 |
|---|---|---|
| 把新消息、动作或工具结果交给记忆方法 | `observe(event)` | 方法需要逐步接收信息时调用 |
| 为当前决策获取记忆 | `retrieve(query, ...)` | 执行前或执行过程中按需调用，可以多次 |
| 从一次完整经历中积累或更新记忆 | `learn(episode)` | 经历完成、所需信息齐全后调用 |
| 提交已经缓冲的处理 | `flush()` | 按方法要求调用 |
| 触发方法特有的更新过程 | `command(name, payload)` | 例如 MemRL 的批次结束、AEL 的定期维护 |

**其中，核心交互入口是 `observe`、`retrieve`、`learn`。每个方法使用其中适合自己的部分，无须每回合全部调用。**

例如：

```text
开始一个任务
    │
    ├─ retrieve：获取已有记忆
    │
    ├─ Agent 使用记忆，执行模型和工具
    │      ├─ 按方法要求 observe：接收新事件
    │      └─ 需要时再次 retrieve
    │
    ├─ 整理完整经历，按方法要求补充反馈
    │
    └─ learn：提交经历，形成或更新记忆
           └─ 需要批次更新的方法，按其规定的时机执行
```

Agent 负责实际使用记忆、执行任务和记录过程。`check`、保存恢复、冻结、清理和统计属于辅助能力，不必混进每个回合的主流程。

**2. `learn` 究竟是什么，必须接收到反馈才能调用吗？**

建议定义为：

> **`learn(episode)`：提交一次完整经历，由所选方法按自身规则形成或更新记忆；所需反馈及更新时机由方法声明。**

这里的“学习”包括提取事实、总结经历、归纳规则、更新记忆价值等，也可以包含方法内部的参数更新。

结合现有方法，可以分两种情况：

| 情况 | 例子 | 对 `learn` 的要求 |
|---|---|---|
| 从内容本身形成记忆 | A-Mem 的整回合写入模式 | 可以从完整交互中形成笔记，反馈可选 |
| 需要任务结果才能学习 | MemRL、MemCon、ExpeL | 需要真实成功标签及完整轨迹，再提交学习 |

因此，**`MemoryEpisode` 可以包含反馈，但并非所有经历都必须有反馈。**需要反馈的方法，在评价晚到时，由调用方保存经历，取得评价后再提交。用户仅在聊天中提供了一条个人偏好，这类信息通常可以直接通过 `observe` 进入记忆。

另一个需要明确的点是：**`learn` 返回，不一定代表所有更新都已完成。**例如现有 MemRL 会把经历加入待处理批次，到规定的批次时机再更新。这属于算法本身的执行规则。

这里也发现了一个实际迁移要求：当前 [Mem0 的 `learn`](/C:/Users/12084/Desktop/研究生/code/MemAtlas/src/mematlas/methods/mem0/method.py:136) 主要提交此前 `observe` 已缓冲的信息。若目标设计允许直接 `learn(episode)` 导入完整历史，就需要让这一入口确实处理经历中的事件，并避免重复写入。这个能力需要在后续重构中落实。
